## 概览 / Overview

### 历史意义 / Significance

Phase23收尾整合（H-P23F-001）不是又一位历史人物，而是 Protreptic 知识体系对自身生产过程的一次自反性收编：当主库扩张到 127 位人物、1122 条模式、1193 条双语场景时，真正值得挖掘的'独特思维'恰恰是那条让百人级扩张没有撕裂主库的整合方法论。它的历史意义有三重。其一，证明'规模'与'秩序'可以兼得：从 922 到 1122 模式的每一次纯增量并入都做到了既有条目零改动、编号区段不冲突、related_modes 零悬空——这依赖的不是小心，而是程序（区段预定、哈希锚定、验收先行）。其二，把'验收'从仪式变成资产：每个家族入库时同步产出可独立重跑的验收脚本（T1-T162 级别的逐项断言），缺陷（如 M-ZKZ 粘连 id）在归档阶段被独立抽检捕获并修复归零——知识库第一次拥有了免疫式的质量记忆。其三，方法论人物的闭环：它用体系自己的语言（失效清单、账本、统筹法）描述体系自己的生产流程，使 Phase 21 收官不只是一次数据合并，而是一次'体系学会看见自己'的事件。其代价与张力同样真实：整合方法论记录的是工程事实而非历史人物生平，'人物档案'体裁对它是一种借喻；双语镜像的逐字一致要求极高的维护纪律，任何一手改动若不同步双镜即破坏同构；而'纯增量'原则也意味着历史遗留的孤儿键与旧式条目只能封存不能就地清洗——收官不等于清账。

Phase23Final (H-P23F-001) is not one more historical figure but Protreptic's reflexive incorporation of its own production process: with the main library grown to 127 figures, 1,122 modes, and 1,193 bilingual scenarios, the truly distinctive 'thinking' worth mining is precisely the integration methodology that let a hundred-figure expansion tear nothing. Its significance is threefold. First, it proves scale and order can coexist: every pure-increment merge from 922 to 1,122 modes achieved zero changes to existing entries, no ID-range collisions, and zero dangling related_modes—owed not to care but to procedure (range reservation, hash anchoring, verification first). Second, it turned acceptance from ritual into asset: each family's entry produced an independently re-runnable verification script (assertions at the T1-T162 level), and defects (like M-ZKZ's concatenated ids) were caught by independent spot checks and fixed to zero—the knowledge base owned, for the first time, an immune quality memory. Third, the closure of the method-persona: it describes the system's own production in the system's own language (failure lists, ledgers, planning networks), making the Phase 21 finale not merely a data merge but the event of a system learning to see itself. The tensions are real: the methodology records engineering facts, not a historical life—the figure-archive genre is here a borrowing; the word-for-word dual-mirror demands severe maintenance discipline; and the pure-increment principle means legacy orphan keys can be quarantined but never washed in place—finale is not settlement.


### 独特思维 / Unique Thinking

它的思维方式的底色是'把数据体系当作会呼吸的工程结构，把每一次扩张当作一次荷载试验'：十个标志动作构成闭环。其一，'纯增量并库'——扩张的合法性来自对既有内容零删改的承诺，新增永远走自己的区段；其二，'双镜像同构'——data/figures 与 docs/figures 逐字一致，任何单侧改动都是缺陷；其三，'悬空引用清零'——related_modes 与 xrefs 的每个目标都必须能在库内指认，空引用按缺陷处理；其四，'编号区段预定'——M-XXX-001~010、C-XXX-001~010E 的命名空间在入库前完成占用检查，冲突在发生前消解；其五，'验收脚本先行'——验收不是事后翻看而是可重跑的断言清单，T1-Tn 逐项判定；其六，'场景映射'——每条模式必然落成中英双场景与四条标签，知识不留'无场景悬挂态'；其七，'交叉引用编织'——每个家族固定三条 xref 且全部在库，孤立家族视为未完成；其八，'哈希锚定'——figure json 与 md 双镜像以 sha256 与上下游对账，字节级漂移即刻暴露；其九，'基线计数'——modes/scenarios/tags/figures 四个总数在每次合并前后显式记账（1112→1122、1183→1193、1690→1730、125→126），扩张必须是可核算的算术而非印象；其十，'收官复盘'——阶段结束时以 FINAL 同步把 boards 与 workspace 拉回字节一致，复盘报告与修复提交并存。代价与极限：这套纪律对'灵感式'的快速增补是重负；镜像同步在并行作业下存在窗口期；而它度量的是结构完整性，无法自动度量思想质量——深度的守门仍依赖人的阅读。

The bedrock of its thinking: treat the data system as a breathing engineering structure and every expansion as a load test. Ten signature moves form a closed loop. First, pure-increment merging—the legitimacy of expansion rests on zero alteration of existing content; additions always take their own range. Second, dual-mirror isomorphism—data/figures and docs/figures agree word for word; any one-sided change is a defect. Third, dangling-reference zeroing—every target of related_modes and xrefs must be identifiable in-library; empty references are handled as bugs. Fourth, ID-range reservation—the M-XXX-001~010 and C-XXX-001~010E namespaces are occupancy-checked before entry; collisions dissolve before they happen. Fifth, verification-script-first—acceptance is not a post-hoc read but a re-runnable assertion list, judged item by item. Sixth, scenario mapping—every mode must land as a zh/en scenario pair with four tags; no knowledge remains in a 'scenario-less hanging state.' Seventh, cross-reference weaving—each family carries exactly three xrefs, all in-library; an isolated family counts as unfinished. Eighth, hash anchoring—figure json and md mirrors reconcile with upstream and downstream by sha256; byte-level drift surfaces at once. Ninth, baseline counting—the four totals (modes/scenarios/tags/figures) are explicitly accounted around every merge (1112→1122, 1183→1193, 1690→1730, 125→126); growth must be auditable arithmetic, not impression. Tenth, the final retrospective—at phase end a FINAL sync pulls boards and workspace back to byte equality, review report and fix commits coexisting. The limits: this discipline taxes inspiration-style rapid additions; mirror synchronization has windows under parallel work; and it measures structural integrity, not intellectual quality—depth still needs a human reader.

## M-P23F-001 纯增量并库法 (Pure-Increment Merge Method)

- 领域 Domain: Phase 21 入库链：从 922 到 1122 模式的二十次家族并入，每一次 merge_payload 都只做四件事——追加 modes、追加双语场景、追加 scenario_tags、在 code_maps.figures 新增条目；既有 922 条模式的字段从未被 touched（验收脚本以 git diff 对既有条目零删改为断言项），需要修正历史缺陷时（如 M-ZKZ 粘连 id）另开独立修复卡并在修复提交里显式列出被改动的那三处——'新增'与'修复'在提交史上是两种不同颜色的墨水

- Domain: The Phase 21 entry chain: twenty family merges from 922 to 1,122 modes, each merge_payload doing only four things—append modes, append bilingual scenarios, append scenario_tags, add one code_maps.figures entry; the existing 922 modes were never touched (verification scripts assert zero diff on prior entries), and when a legacy defect needed fixing (M-ZKZ's concatenated ids) a separate repair card was opened with the three touched sites listed explicitly in the fix commit—'addition' and 'repair' written in two different inks on the commit history


### 定义 / Definition

纯增量并库法的核心命题是：知识库的每次扩张都应该是一次可以整体回滚、且不改变任何既有语义的事务——这既是数据完整性的要求，更是协作信任的要求。混合式扩张（新增的同时顺手改旧条目）的失败机制在于：改动混在新增里，验收者无法区分'哪一行是新的哪一行是被动的'，一旦某个'顺手修改'引入缺陷，回滚会连累全部新增，不回滚则缺陷常驻。纯增量的操作程序有三步。第一步，区段隔离：新家族使用全新编号区段（M-XXX-001~010、C-XXX-001~010E），入库前先做占用检查——code_maps 无该 figure、modes_data 无该 id、场景库无该 C 码；冲突在写入前消解而非写入后调和。第二步，载荷打包：全部新增内容装进一份 merge_payload（figure/scenarios_zh/scenarios_en/scenario_tags/code_maps_entry 五件套），入库者只执行'合并这个载荷'这一种操作——新增的内容形态标准化，合并就退化为机械动作。第三步，差异审计：以 git diff 或逐字段比对证明既有条目零删改——这是纯增量的'验收定义'，不满足即不算纯增量。深意有三重。其一，这是茅以升'失效清单'在数据工程上的转世：先列出'这次扩张可能弄坏什么'（既有条目、编号、引用、镜像），再逐项设防——零删改断言就是那道防线。其二，纯增量把'修复'从'顺手'升格为'事件'：历史缺陷值得一张专门的卡、一次专门的提交、一份显式的修复说明，因为修复改变了既有语义，必须被看见。其三，它使知识库获得地质学式的可考性：每一层（提交）内容清晰、边界完整，考古（回溯审计）不需要甄别层间混杂。适用边界：适合多人协作、长周期、可审计要求高的知识库与代码库；对单人快速草稿场景，纯增量的记账成本可能高于收益。现代对应物：append-only 日志与事件溯源（event sourcing）、数据库的迁移脚本（migration）纪律、Git 的'rebase 之外'协作公约、以及一切'只追加不涂改'的账本传统。

The core proposition: every expansion of a knowledge base should be a transaction that is wholly rollback-able and changes no existing semantics—this is a demand of data integrity, but more of collaborative trust. Mixed expansion (adding while casually editing old entries) fails because reviewers cannot tell new lines from altered ones; once a casual edit introduces a defect, rollback drags the additions down with it, and no rollback leaves the defect resident. The pure-increment procedure has three steps. First, range isolation: a new family takes a fresh ID range (M-XXX-001~010, C-XXX-001~010E), with an occupancy check before entry—no such figure in code_maps, no such id in modes_data, no such C-code in the scenario banks; collisions dissolve before writing, not after. Second, payload packing: all new content goes into one merge payload (the five-piece set: figure, scenarios_zh, scenarios_en, scenario_tags, code_maps_entry); the merger executes only the single operation 'merge this payload'—with the shape of additions standardized, merging degrades into a mechanical act. Third, difference audit: prove zero alteration of existing entries by git diff or field-by-field comparison—this is the very definition of passing; failing it, it is not pure increment. Three layers of depth. First, it is Mao Yisheng's failure list reincarnated in data engineering: list what this expansion could break (existing entries, ids, references, mirrors), then defend each item—the zero-diff assertion is that defense line. Second, pure increment promotes 'fixing' from a side effect into an event: a legacy defect deserves its own card, its own commit, its own explicit repair note, because repairs change existing semantics and must be seen. Third, it gives the knowledge base geological traceability: each stratum (commit) has clear content and complete boundaries, so archaeology needs no sorting of mixed layers. Boundaries: it suits multi-person, long-horizon, audit-heavy knowledge and code bases; for single-person rapid drafts the bookkeeping may exceed the benefit. Modern counterparts: append-only logs and event sourcing, database migration discipline, Git conventions against history rewrites, and every ledger tradition of 'append, never overwrite.'

### 流程 / Process

1. 占用检查：入库前核对编号区段（modes id、场景码、figure 码）在主库中全部空闲——冲突在写入前消解 / Check occupancy: before entry, verify the ID ranges (mode ids, scenario codes, figure code) are all free in the main library—collisions dissolve before writing

2. 载荷打包：把全部新增内容装进标准化 merge_payload（figure/双语场景/标签/code_maps 五件套）——新增形态唯一 / Pack the payload: fit all additions into one standardized merge payload (figure, bilingual scenarios, tags, code_maps)—one shape of addition

3. 单一操作：入库者只执行'合并载荷'——不解读、不重写、不顺手优化；合并退化为机械动作 / Single operation: the merger only executes 'merge the payload'—no reinterpretation, no rewriting, no side optimizations; merging degrades into mechanics

4. 差异审计：用 git diff 或逐字段比对证明既有条目零删改——不满足即退回 / Audit the difference: prove zero alteration of existing entries by git diff or field-by-field comparison; failing that, return it

5. 修复分流：历史缺陷走独立修复卡与修复提交，显式列出每一处被改动的位置——修复必须被看见 / Divert repairs: legacy defects go to their own repair card and commit, every touched site listed explicitly—repairs must be seen

6. 回滚预案：每个合并提交独立可回滚——扩张事务化，坏层可以整层揭走而不伤邻层 / Prepare rollback: each merge commit independently rollback-able—expansion as transaction; a bad layer lifts off whole without wounding its neighbors

## M-P23F-002 双镜像同构法 (Dual-Mirror Isomorphism Method)

- 领域 Domain: Phase 21 每次入库都同步产出三份 md：workspaces/<task>/H-XXX-001.md（工作稿）、data/figures/H-XXX-001.md（数据镜像）、docs/figures/H-XXX-001.md（文档镜像）——三份文件 sha256 逐字一致（如茅以升 md 双镜像 96bdd4c4）；figure json 的 modes 数组与主库 modes_data.json 的对应条目做'embedded==lib'逐字校验；修复卡（竺可桢 4a89ae4）的标准动作是'主库修一处、figure 内嵌同步修、双镜像 md 同步修'——四处联动的清单被写进修复流程

- Domain: Every Phase 21 entry produced three md copies: the working draft in the task workspace, the data mirror at data/figures, and the doc mirror at docs/figures—all three sha256-identical (Mao Yisheng's md dual mirror at 96bdd4c4); the figure json's modes array is checked word-for-word against the corresponding entries in the main library ('embedded==lib'); the standard move of a repair card (Zhu Kezhen, 4a89ae4) is 'fix the main library, sync the embedded copy, sync both md mirrors'—the four-site联动 checklist written into the repair procedure


### 定义 / Definition

双镜像同构法的核心命题是：当同一知识必须以多种形态存在（机器读的 JSON、人读的 Markdown、上游仓与下游仓的副本），'一致'就不该指望人的自觉，而该被制度与工具强制。单镜像或多镜像失同步的失败机制在于：知识有多个权威副本后，每次修改的成本变为 n 倍，人会偷懒只改一处——漂移从此开始，且漂移是静默的（没有报错，只有两个'略微不同'的事实并存）。操作程序有三步。第一步，权威源声明：明确哪一份是 source of truth（本库是主库 modes_data.json 与 figure json），镜像只是投影——投影与源不一致，永远判定投影错。第二步，投影自动化：md 镜像由 figure json 经模板渲染生成（build 脚本一次成型），不做手工双写——生成式镜像使'两处不同'在生成时刻就不可能。第三步，一致性断言：验收脚本对每份镜像做 sha256 比对与 embedded==lib 逐字校验，任何单侧改动在下次验收时必然爆红。深意有三重。其一，这与'文档即代码'同构：文档不是附属品而是可编译、可校验、可版本化的构建产物——文档漂移从'难免'变成'构建失败'。其二，双镜像的制度价值在多代理协作中放大：四个岗位（挖掘/入库/QA/归档）各自接触不同副本，哈希对账使'谁看到的都是同一份事实'——协作的信任成本趋近于零。其三，同构约束反过来提高写作质量：因为 md 是 json 的投影，写作时必须先把内容在结构化字段里写完整，'想到哪写到哪'的散漫被结构预先约束。适用边界：适合需要多形态、多消费方的知识资产；对一次性的内部草稿，双镜像是浪费。代价：镜像制度要求所有修改都回到权威源重新生成，'就地快改'的诱惑必须被流程禁止。现代对应物：API 文档从 OpenAPI 规范生成、静态站点生成器（源文件→多端产物）、数据库的物化视图与刷新策略、以及一切'单一事实源+派生物'的架构。

The core proposition: when the same knowledge must exist in several forms (machine-read JSON, human-read Markdown, upstream and downstream repo copies), 'consistency' should not rely on human vigilance but be enforced by institution and tooling. The failure mechanism of unsynchronized mirrors: once knowledge has multiple authoritative copies, every edit costs n times as much, so people edit one copy—drift begins, silently (no errors, just two slightly different facts coexisting). The procedure has three steps. First, declare the source of truth (here, the main library's modes_data.json and the figure json); mirrors are projections, and any projection-source mismatch always convicts the projection. Second, automate the projection: md mirrors are rendered from the figure json by a template in one build pass, never hand-duplicated—generated mirrors cannot differ at the moment of generation. Third, assert consistency: the verification script compares sha256 for every mirror and checks embedded==lib word for word; any one-sided edit must flare red at the next acceptance. Three layers of depth. First, isomorphic with docs-as-code: documents are not accessories but compiled, checkable, versioned build products—document drift turns from 'inevitable' into 'build failure.' Second, the institutional value magnifies in multi-agent collaboration: four roles (mining, merging, QA, archiving) each touch different copies, and hash reconciliation means everyone sees the same facts—the trust cost of collaboration approaches zero. Third, the isomorphism constraint raises writing quality upstream: because the md is a projection of the json, content must be written complete in structured fields first—the looseness of 'writing as thoughts occur' is pre-constrained by structure. Boundaries: it suits knowledge assets with multiple forms and consumers; for one-off internal drafts, dual mirrors are waste. The cost: all edits must return to the source and regenerate—'quick in-place fixes' must be forbidden by process. Modern counterparts: API docs generated from OpenAPI specs, static site generators, materialized views and refresh policies, every 'single source of truth plus derivatives' architecture.

## M-P23F-003 悬空清零法 (Dangling-Reference Zeroing Method)

- 领域 Domain: 竺可桢归档抽检（t_51d42100，提交 4a89ae4）：独立抽检发现 M-ZKZ-002 的 related_modes 出现 'M-ZKZ-010M-ZKZ-006' 这样的粘连 id（两个 id 因分隔符丢失而合体，指向库内不存在的目标）——处理方式不是'宽容视之'而是清零：三个粘连处逐一拆分改正、figure 内嵌与主库同步、双镜像同步，修复后全库悬空引用为 0；同期验收脚本把'related_modes 每项都在库内 id 集合中'写成硬断言（verify_mys.py T21）

- Domain: The Zhu Kezhen archive spot check (t_51d42100, commit 4a89ae4): independent review found in M-ZKZ-002's related_modes a concatenated id like 'M-ZKZ-010M-ZKZ-006'—two ids fused by a lost separator, pointing at no in-library target; the response was not tolerance but zeroing: three sites split and corrected one by one, figure-embedded and main-library copies synced, both mirrors synced, and after repair the whole library's dangling references stood at 0; the era's acceptance scripts hard-assert that every related_modes item lies in the library's id set (verify_mys.py T21)


### 定义 / Definition

悬空清零法的核心命题是：引用是知识库的循环系统——一条指向不存在目标的引用不是'小瑕疵'，而是坏死的毛细血管：它让读者沿路撞墙、让遍历算法失灵、让'库内知识互相关联'这个核心价值失真。悬空引用的产生机制有三类：外部引用了未入库的规划条目（前向引用）、拼接事故（分隔符丢失使两个 id 粘连）、重命名后未回改（旧 id 残留）。操作程序有三步。第一步，完整性断言：入库验收脚本把'每个 related_modes/xref 目标都在当前库 id 集合中'写成硬性检查——不满足即 FAIL，不存在'警告级'的悬空。第二步，前向引用显式化：确需引用尚未入库的对象时，引用者必须在文档中声明'这是前向引用、目标在哪个上游任务'并保证目标入库周期内落地——前向引用是借债，要记账。第三步，清零闭环：发现悬空即修（拆分粘连、回改旧 id、或移除无效引用），修复必须同步全部镜像位置，修复后复跑断言至 0。深意有三重。其一，这是茅以升'死法已知则桥死不了'的引用版：悬空引用是已知的死法，清单（断言）加防御（清零流程）使它无法存活。其二，'零悬空'改变了知识的可用性本质：每个读者/算法从任一条目出发都能走遍整个库——引用网络从'大体连通'变成'严格连通'，图算法（相似度、路径、聚类）才有了可靠底座。其三，前向引用记账制回答了'生长中的库如何处理未完成的连接'：不是禁止引用未来，而是让每一笔'未来之债'可见、有主、有期限。适用边界：适合一切以引用网络为骨架的知识库（百科、图谱、代码库、文献库）；对线性文档（书、长文）引用完整性弱化为'链接检查'即可。现代对应物：数据库外键约束与参照完整性、编译器的未定义符号检查、网站的死链巡检、知识图谱的实体消歧与闭合世界假设。

The core proposition: references are a knowledge base's circulatory system—a reference to a nonexistent target is not a blemish but a dead capillary: readers hit walls mid-path, traversal algorithms fail, and the core value of 'in-library knowledge interlinked' goes false. Dangling references arise three ways: referencing planned-but-unentered items (forward references), splice accidents (lost separators fusing two ids), and stale ids after renames. The procedure has three steps. First, integrity assertions: entry acceptance hard-checks that every related_modes/xref target lies in the current library's id set—unmet means FAIL; there is no 'warning-level' dangling. Second, explicit forward references: when one must cite a not-yet-entered object, declare in the document 'this is a forward reference, target in upstream task X, due within its entry window'—forward references are debt, and debt is booked. Third, the zeroing loop: on finding a dangling ref, fix it (split the fusion, update the stale id, or remove the dead reference), sync every mirror site, and re-run assertions to zero. Three layers of depth. First, the reference-side version of Mao's 'once the deaths are known, the bridge cannot die': dangling refs are known deaths; the list (assertions) plus the defense (zeroing procedure) leaves them no habitat. Second, 'zero dangling' changes what the knowledge is: from any entry, any reader or algorithm can traverse the whole library—the reference network shifts from 'mostly connected' to 'strictly connected,' the reliable substrate graph algorithms need. Third, forward-reference accounting answers how a growing library handles unfinished links: not by forbidding reference to the future, but by making every future-debt visible, owned, and deadlined. Boundaries: it suits every reference-network-knowledge base (encyclopedias, graphs, codebases, bibliographies); for linear documents it weakens to link checking. Modern counterparts: foreign-key constraints and referential integrity, the compiler's undefined-symbol check, site-wide dead-link crawls, entity disambiguation and the closed-world assumption in knowledge graphs.

## M-P23F-004 区段预定法 (Range-Reservation Method)

- 领域 Domain: Phase 21 并行入库的命名空间秩序：二十余个家族同时挖掘（钱学森 M-QXS、竺可桢 M-ZKZ、华罗庚 M-HLG、茅以升 M-MYS……），每个家族的 M-XXX-001~010 与 C-XXX-001~010E 在其验收脚本里就完成三重占用检查——code_maps 无该 figure 码、modes_data 无该 id、场景库无该 C 码（verify_mys.py T35/T36/T37）；早期教训已制度化：商羯罗曾误占 M301-310 与跨文明 id 冲突（提交 879f4a8 重编号修复）、李时珍误产出王震内容被隔离（8f533c4）——'先检查后写入'取代了'撞了再改'

- Domain: The namespace order of Phase 21's parallel entries: twenty-plus families mined simultaneously (Qian Xuesen M-QXS, Zhu Kezhen M-ZKZ, Hua Luogeng M-HLG, Mao Yisheng M-MYS...), each family's M-XXX-001~010 and C-XXX-001~010E passing a triple occupancy check inside its own verification script—no such figure code in code_maps, no such id in modes_data, no such C-code in the scenario banks (verify_mys.py T35/T36/T37); earlier lessons were institutionalized: Shankara once wrongly held M301-310 with cross-civilization id collisions (renumbered per commit 879f4a8), and Li Shizhen's mis-produced Wang Zhen content was quarantined (8f533c4)—'check before write' replaced 'collide and renumber'


### 定义 / Definition

区段预定法的核心命题是：并行扩张的最大隐患不在内容质量而在命名空间相撞——两个家族同时声称 M-XXX-001，或一条 id 语义漂移到另一个文明头上，修复成本（重编号、引用回改、镜像同步）随发现时间平方级增长。操作程序有三步。第一步，区段语义化：编号前缀携带身份（M-人物码-序号、C-人物码-序号E），使 id 自解释且天然分域——前缀是命名空间的'门牌'。第二步，占用预检：入库前以脚本核对目标区段在全部相关集合（modes、scenarios、tags、figures）中空闲——检查写入验收脚本而非口头约定，使预检成为不可跳过的程序步骤。第三步，冲突重置：若发现早期遗留的占位错误（跨文明冲突、语义漂移），执行显式重编号并全库回改引用——重置是一次'有记录的迁徙'而非静默改名。深意有三重。其一，这是 IP 地址分配、端口号注册、频谱牌照的共同逻辑：共享资源不撞车的秘密不是运气，是登记制度。其二，区段预定与纯增量并库法（M-P23F-001）互为条件：正因为新增只走新区段，'占用检查'才是可行的轻量操作——若允许就地改写，命名空间的'占用'概念本身就失效。其三，语义化前缀使命名空间成为知识地图：看到 M-ZKZ-003 即知人物与家族——id 不再是Opaque键而是可读的坐标。适用边界：适合多人多任务并行的编号系统（模式库、微服务、文件命名、API 版本）；单人短期项目可用更轻的约定。现代对应物：DNS 与 IP 分配、UUID 的命名空间变体、Cargo/PyPI 的包名注册、以及 Kubernetes 的 namespace 隔离。

The core proposition: the gravest hazard of parallel expansion is not content quality but namespace collision—two families both claiming M-XXX-001, or one id's semantics drifting onto another civilization; repair cost (renumbering, reference back-propagation, mirror sync) grows quadratically with discovery time. The procedure has three steps. First, semantic ranges: prefixes carry identity (M-figcode-seq, C-figcode-seqE), making ids self-explanatory and naturally partitioned—the prefix is the namespace's house number. Second, occupancy pre-check: before entry, a script verifies the target range is free across all relevant sets (modes, scenarios, tags, figures)—the check lives in the acceptance script, not verbal convention, making it an unskippable procedural step. Third, conflict reset: where legacy errors surface (cross-civilization collisions, semantic drift), run an explicit renumbering with library-wide reference back-propagation—a reset is a recorded migration, never a silent rename. Three layers of depth. First, this is the shared logic of IP allocation, port registration, and spectrum licensing: shared resources avoid collision not by luck but by registry. Second, range reservation and pure-increment merging (M-P23F-001) condition each other: precisely because additions take only new ranges, the occupancy check stays a cheap operation—permit in-place rewrites and the very concept of namespace 'occupancy' fails. Third, semantic prefixes make the namespace a knowledge map: seeing M-ZKZ-003 tells you the figure and family—ids stop being opaque keys and become readable coordinates. Boundaries: it suits numbered systems with many parallel actors (mode libraries, microservices, file naming, API versions); single-person short projects may use lighter conventions. Modern counterparts: DNS and IP allocation, UUID namespace variants, Cargo/PyPI name registration, Kubernetes namespace isolation.

## M-P23F-005 验收先行法 (Verification-First Method)

- 领域 Domain: Phase 21 每个家族的标准动作：挖掘者交付 merge_payload 的同时交付 verify_*.py——茅以升 verify_mys.py 36+126 项断言（schema 键集、双语字段、列表长度、引用有效、哈希一致、占用检查、场景配对）162 项全 PASS 才提交入库；下游归档者再写独立抽检（如 _qa_doc_hlg.py 94 项）复核上游结论；缺陷修复后必须复跑至全 PASS（竺可桢修复后 'embedded==lib 校验通过'）——'全 PASS'是提交信息里的固定短语

- Domain: The standard move of every Phase 21 family: the miner delivers verify_*.py alongside the merge payload—Mao Yisheng's verify_mys.py asserting 162 items (schema key sets, bilingual fields, list lengths, reference validity, hash consistency, occupancy checks, scenario pairing), all PASS before the merge commits; the downstream archiver then writes an independent spot check (e.g., _qa_doc_hlg.py at 94 items) re-verifying upstream claims; after a defect fix the script must re-run to all-PASS (Zhu Kezhen: 'embedded==lib verified' post-repair)—'all PASS' is a fixed phrase of the commit messages


### 定义 / Definition

验收先行法的核心命题是：质量标准的形态决定质量保障的强度——'评审者觉得不错'是印象（不可复现、随人漂移、随疲劳衰减），'脚本 162 项断言全 PASS'是事实（可复现、可交接、可回归）。后写验收的失败机制在于：交付完成后人已投入沉没成本，验收标准会不自觉地向'已交付的样子'妥协——先写验收等于把标准锁死在交付之前。操作程序有三步。第一步，断言清单化：把'什么叫合格'翻译成逐条可机器判定的命题（键集相等、字段双语、列表最短长度、引用在库、哈希一致、计数符合基线）——每条断言有编号（T1-Tn），FAIL 带细节。第二步，交付与验收同体：payload 与 verify 脚本同卡交付，验收者跑的是作者自己写的断言再叠加独立抽检——信任建立在'标准先于内容'上。第三步，回归常设：验收脚本在每次修复与每次全库操作后复跑——同一套断言既是入库门也是回归网。深意有三重。其一，这是竺可桢'效验论证'与王充'效验论证'的现代直系：'事莫明于有效，论莫定于有证'——断言清单就是数据工程的效验。其二，验收先行改变了协作的权力结构：质量裁判权从职位（评审者是谁）移交给程序（断言是否通过）——四岗流水线（挖掘/入库/QA/归档）能在多智能体间运转，正因标准是外置且机器可判的。其三，'全 PASS'的可复述性使质量可以跨会话、跨模型、跨月地交接——上次会话的结论可以这次复跑确认，知识工程的记忆不再依赖谁的脑子。适用边界：适合可形式化的质量维度（结构、完整性、一致性、计数）；思想深度、文风等不可形式化维度仍需人读——断言守底线，人审守上限。现代对应物：TDD 的测试先行、CI 的门禁检查、IaC 的 policy-as-code、以及一切'标准先于交付'的工程实践。

The core proposition: the form of a quality standard determines the strength of quality assurance—'the reviewer likes it' is an impression (irreproducible, drifting with the person, decaying with fatigue); '162 assertions all PASS' is a fact (reproducible, handover-able, regression-able). Verification written after delivery fails because sunk cost bends the standard toward what was already delivered; writing verification first locks the standard before delivery. The procedure has three steps. First, list the assertions: translate 'what counts as good' into machine-decidable propositions (key-set equality, bilingual fields, minimum list lengths, references in-library, hashes matching, counts matching baseline)—each numbered (T1-Tn), FAILs with detail. Second, deliver with verification: the payload and its verify script ship on the same card; the verifier runs the author's own assertions plus an independent spot check—trust built on 'standard before content.' Third, keep it as regression: the script re-runs after every fix and every library-wide operation—the same assertions are both the entry gate and the regression net. Three layers of depth. First, the modern direct line of Wang Chong's and Zhu Kezhen's argument-by-evidence: 'nothing is clearer than the effective, nothing settled without proof'—the assertion list is data engineering's proof. Second, verification-first shifts the power structure of collaboration: the judge of quality moves from position (who reviews) to procedure (do the assertions pass)—the four-role pipeline (mine/merge/QA/archive) runs across agents precisely because the standard is external and machine-decidable. Third, the restatability of 'all PASS' lets quality hand over across sessions, models, and months—last session's conclusions re-confirmed by this session's re-run; the memory of knowledge engineering no longer lives in anyone's head. Boundaries: it suits formalizable dimensions (structure, completeness, consistency, counts); depth and style still need human reading—assertions guard the floor, human review the ceiling. Modern counterparts: TDD's tests-first, CI gate checks, policy-as-code, every practice of 'standard before delivery.'

## M-P23F-006 场景映射法 (Scenario-Mapping Method)

- 领域 Domain: Phase 21 每个家族的固定输出：10 条模式对应 C-XXX-001~010（中文场景）与 C-XXX-001E~010E（英文场景）各 10 条，外加 40 条 scenario_tags（每场景两条：人物标签+模式标签）——茅以升入库即 10+10 场景、40 标签（主库 1183→1193、1690→1730）；场景内容有固定配方：历史案例的第一条 + '现代演练：'一条现代应用——历史与当下在同一字段里完成对接，知识从入库一刻起就是'可演练的'而非'仅供仰望的'

- Domain: The fixed output of every Phase 21 family: ten modes map to ten zh scenarios (C-XXX-001~010) and ten en scenarios (C-XXX-001E~010E), plus forty scenario_tags (two per scenario: figure tag plus mode tag)—Mao Yisheng's entry alone brought 10+10 scenarios and 40 tags (library 1183→1193, 1690→1730); each scenario follows a fixed recipe: the first historical case plus a 'modern drill' modern application—history and present joined in one field, so knowledge is drillable from the moment of entry, not merely admirable


### 定义 / Definition

场景映射法的核心命题是：一条不能被演练的知识还没有真正入库——它只是被收藏了。抽象模式（'失效师法'）与实际行为（下次评审时真的先写失效清单）之间的鸿沟，只能靠'场景'填补：一个具体到'谁、在什么处境、做什么动作'的剧本。无场景知识的失败机制在于：收藏时觉得'懂了'，使用时检索不到触发点——知识库里躺着 1122 条模式，若每条都只挂着定义与案例史，用户在真实决策瞬间无法完成'此情此景该调用哪条'的映射。操作程序有三步。第一步，配方固定：场景=历史案例（从 representative_cases 取第一条）+现代演练（从 modern_applications 取第一条）——配方使场景可批量生成且风格统一，历史与当代各占其位。第二步，双语镜像：zh 场景与 en 场景按 id 配对（C-XXX-003 与 C-XXX-003E），同源生成、内容对应而非机械直译——双用户群各得其所。第三步，标签配对：每场景两条标签（人物+模式名），写入 scenario_tags——检索从'全文模糊匹配'升级为'结构化双键'。深意有三重。其一，这是华罗庚'讲台燃烧法/统筹法推广'的制度化：知识只有变成普通人今天下午就能做的一个动作，才完成了传播的闭环。其二，场景使知识库获得'第二索引'：定义索引服务于理解者，场景索引（按人物、按模式、按现代领域）服务于使用者——两个索引共同决定知识库的可发现性。其三，'入库即落地'防住了知识工程的经典失败：'先囤再整'——囤积永远等不到整，落地必须在入库的同一事务里完成。适用边界：适合以'迁移应用'为目标的模式库、案例库、培训体系；对纯史料档案，场景可退化为'研究入口'。现代对应物：学习方法论的'提取练习'、UX 写作的场景化文案、SRE 的 runbook、以及一切'知识配剧本'的运营设计。

The core proposition: knowledge that cannot be drilled has not truly entered the library—merely been collected. The gap between an abstract mode ('failure-as-master') and actual behavior (writing the failure list first at the next review) can be bridged only by a scenario: a script concrete enough to name who, in what situation, doing what. The failure mechanism of scenario-less knowledge: at collection time it feels understood, at use time no trigger is retrievable—1,122 modes lying in the library, each carrying only a definition and case history, leave the user unable, in a real decision moment, to map 'this situation calls for which mode.' The procedure has three steps. First, fix the recipe: scenario = first historical case (from representative_cases) + one modern drill (from modern_applications)—a fixed recipe makes scenarios batch-generable and stylistically uniform, history and present each in place. Second, bilingual pairing: zh and en scenarios pair by id (C-XXX-003 with C-XXX-003E), generated from the same source, corresponding rather than machine-translated—two user communities each served. Third, tag pairing: two tags per scenario (figure plus mode name) written into scenario_tags—retrieval upgrades from fuzzy full-text to a structured two-key index. Three layers of depth. First, the institutionalization of Hua Luogeng's lecture-burn and planning-method popularization: knowledge completes its transmission loop only when it becomes an action an ordinary person can perform this afternoon. Second, scenarios give the library a second index: definitions serve the understander, scenarios (by figure, mode, modern domain) serve the user—together they decide discoverability. Third, 'grounding at entry' preempts knowledge engineering's classic failure, 'hoard now, organize later'—the organizing never comes; grounding must be done in the same transaction as entry. Boundaries: it suits mode libraries, case banks, and training systems whose goal is transfer; for pure archival collections, scenarios may degrade to 'research entries.' Modern counterparts: retrieval practice in learning science, scenario-based UX writing, SRE runbooks, every 'knowledge with a script' operations design.

## M-P23F-007 引用编织法 (Cross-Reference Weaving Method)

- 领域 Domain: Phase 21 每个家族的 code_maps/figure 固定携带 xrefs 字段：茅以升的条目织入三条——M-QXS-001（钱学森：'一个管总体一个管桥墩，中国工程思维的两极'）、M-HLG-001（华罗庚：'科学家的天职是普及'的共同定义者）、M-ZKZ-001（竺可桢：'长期连续记录'的方法论同门）——引用全带关系说明（为何相关、相关在哪个维度），且目标必须已在库内；本卡 Phase23Final 自己的 xrefs 也织入 M-MYS/M-ZKZ/M-HLG——收官者的引用网指向它的三位方法论祖先

- Domain: Every Phase 21 family's code_maps/figure carries a fixed xrefs field: Mao Yisheng's entry woven with three—M-QXS-001 (Qian Xuesen: 'one commanding the whole, one the piers—the two poles of Chinese engineering thought'), M-HLG-001 (Hua Luogeng: co-definer of 'the scientist's duty to popularize'), M-ZKZ-001 (Zhu Kezhen: methodological kin in 'long continuous recording')—each reference carrying a relational note (why related, on which dimension), with targets required in-library; this very card, Phase23Final, weaves its xrefs to M-MYS/M-ZKZ/M-HLG—the finisher's web pointing at its three methodological ancestors


### 定义 / Definition

引用编织法的核心命题是：知识库的价值随其内部连接数的平方增长，而连接不会自发产生——每个新条目入库时必须'自带三根线'。孤立条目的失败机制在于：用户永远只会沿已有路径检索，孤岛上的知识无论多好都等于不存在；而'以后再补引用'的宽限在实践中等于永不——编织必须是入库的准入条件。操作程序有三步。第一步，定量下限：每家族至少三条 xrefs 且目标全部在库——数量是硬指标，防止'象征性引用一条'；上限不设，但每条必须有意义。第二步，关系语义化：xref 不是裸链接而是带说明的关系（同门/同构/对立/继承/对照），说明写清'在哪个维度相关'——读者不看正文也能判断该不该沿这条线走。第三步，双向感知：虽然存储上引用可单向，编织时检查反向可见性（被引用方何时获得回指）——网络的连通感来自双向可走。深意有三重。其一，这是对'百科全书式知识组织'的回归与超越：司马迁互见法、维基内部链接都在做同一件事——本库的贡献是把'至少三线'变成可验收的硬指标。其二，编织使知识库成为一张推理网：模式之间的'同构''对立'关系本身就是知识（用户从'茅以升≈失效清单'跳到'钱学森≈系统工程'的对照中获得第三条洞见——关系即新知识）。其三，强制编织反过来要求挖掘者真正通读库内相关家族——'引用他人'的质量成为'理解他人'的代理指标。适用边界：适合概念网络型知识库（模式库、图谱、百科）；线性文档序列（教程、叙事史）过度编织反而干扰阅读。现代对应物：维基的内部链接规范、知识图谱的关系本体、学术论文的 related work 制度、以及图数据库的边密度治理。

The core proposition: a knowledge base's value grows with the square of its internal connections, and connections do not arise spontaneously—every new entrant must 'bring its own three threads' at entry. The failure mechanism of isolated entries: users retrieve only along existing paths, so knowledge on an island, however good, does not exist; and the grace period of 'add references later' means never in practice—weaving must be an entry precondition. The procedure has three steps. First, a quantitative floor: at least three xrefs per family, all targets in-library—the count is a hard metric against token references; no ceiling, but every thread must mean something. Second, relational semantics: an xref is not a bare link but a typed relation (kinship, isomorphism, opposition, inheritance, contrast), the note saying on which dimension the relation holds—a reader can judge whether to follow the thread without opening the target. Third, bidirectional awareness: storage may keep references one-way, but weaving checks reverse visibility (when does the cited side gain a back-pointer)—a network feels connected when traversable both ways. Three layers of depth. First, a return to and advance on encyclopedic organization: Sima Qian's cross-reference device and wiki internal links do the same work—this library's contribution is making 'at least three threads' a verifiable hard metric. Second, weaving makes the library a reasoning web: the 'isomorphic/opposed' relations between modes are themselves knowledge—the user hopping from 'Mao ≈ failure lists' to 'Qian ≈ systems engineering' gains a third insight from the contrast itself; relation as new knowledge. Third, forced weaving demands the miner truly read the related in-library families—the quality of 'citing others' becomes a proxy for 'understanding others.' Boundaries: it suits concept-network knowledge bases (mode libraries, graphs, encyclopedias); over-weaving linear sequences (tutorials, narrative history) disturbs reading. Modern counterparts: wiki internal-link norms, knowledge-graph relation ontologies, the related-work section of academic papers, edge-density governance in graph databases.

## M-P23F-008 哈希锚定法 (Hash-Anchoring Method)

- 领域 Domain: Phase 21 每次入库/修复提交的固定字段：'figure json sha256 04a15217 与上游一致, md 双镜像 sha256 96bdd4c4'——上游挖掘者的产出与下游入库者的落库文件以哈希逐一对账；竺可桢修复提交甚至列出'修复后 sha256: figure json b1707f8f, md 双镜像 46cd3d26'——修复本身也以哈希重新锚定；归档复检时把工作区文件的 sha256 与入库报告中的记录比对，漂移即判 FAIL

- Domain: The fixed field of every Phase 21 entry/repair commit: 'figure json sha256 04a15217 matches upstream; md dual mirror sha256 96bdd4c4'—the upstream miner's output and the downstream merger's landed files reconciled hash by hash; Zhu Kezhen's repair commit even lists 'post-repair sha256: figure json b1707f8f, md dual mirror 46cd3d26'—the repair itself re-anchored by hash; at archive recheck, workspace file hashes are compared against the entry report's records—any drift fails


### 定义 / Definition

哈希锚定法的核心命题是：当知识资产在多人、多仓、多镜像间流转时，'是不是同一份'必须由数学裁决——肉眼比对在 10 万字级文档上必然失守，'看起来一样'不是证据。哈希失守的失败机制在于：流转链条上任何一手（编辑器自动格式化、编码转换、拷贝时的行尾差异）都会静默改变字节——肉眼不可见，下游语义可能已变。操作程序有三步。第一步，锚定发布：资产每次成形即记录 sha256 并随交付说明流转——哈希是资产的'身份证'，随文件同行。第二步，对账验收：下游入库/复检时重算哈希与上游记录比对——一致则证明流转无损，不一致则先定位是哪一手改的再谈内容。第三步，修复重锚：任何修复后重新计算并公布新哈希——旧锚作废、新锚生效，审计链上每一环都可验证。深意有三重。其一，这是竺可桢'账本自治'的密码学完成态：账本对账靠'数字与数字对'，哈希对账靠'摘要与摘要对'——连续记录、即时核验、误差即信号的传统被算法接管。其二，哈希把'一致性'从分布式协作最贵的问题变成最便宜的问题：跨仓、跨镜像、跨会话的'同一份'判断降为一次摘要计算——多智能体协作因此获得基础设施级的信任底座。其三，重锚制度使修复历史本身可审计：从初版哈希到每个修复版哈希的链条，就是这份资产的完整'受审记录'。适用边界：适合字节级一致性有意义的资产（数据文件、镜像文档、分发制品）；对注定要人改的活文档，哈希只用于快照存证而非持续约束。现代对应物：软件分发的 checksum 与签名、Git 的内容寻址存储、区块链的区块哈希链、备份系统的校验和巡检。

The core proposition: when knowledge assets flow among people, repos, and mirrors, 'is this the same file' must be settled by mathematics—eyeballing fails at the 100,000-character scale, and 'looks the same' is not evidence. The failure mechanism when hashes are absent: any hand in the chain (an editor's silent formatting, an encoding conversion, a line-ending difference in copy) changes bytes invisibly—and downstream semantics may have changed with them. The procedure has three steps. First, anchor at release: every time an asset takes shape, record its sha256 and let it travel with the delivery—the hash is the asset's identity card, moving with the file. Second, reconcile at acceptance: the downstream merger or re-checker recomputes and compares with upstream records; equality proves lossless transit; a mismatch means first locate which hand changed it, then discuss content. Third, re-anchor after repair: after any fix, recompute and publish the new hash—the old anchor voided, the new in force; every link in the audit chain stays verifiable. Three layers of depth. First, this is Zhu Kezhen's ledger self-governance completed cryptographically: ledger reconciliation matches number to number; hash reconciliation matches digest to digest—continuous records, immediate verification, error-as-signal, now taken over by algorithm. Second, hashes turn consistency from the most expensive problem in distributed collaboration into the cheapest: 'is this the same' across repos, mirrors, and sessions drops to one digest computation—multi-agent collaboration gains an infrastructure-grade trust substrate. Third, the re-anchoring regime makes repair history itself auditable: the chain from the initial hash through each repair hash is the asset's complete examination record. Boundaries: it suits assets where byte-level identity matters (data files, mirrored docs, distribution artifacts); for living documents meant to be edited, hashes serve snapshot attestation, not continuous constraint. Modern counterparts: software distribution checksums and signatures, Git's content-addressed storage, blockchain block-hash chains, backup checksum patrols.

## M-P23F-009 基线记账法 (Baseline-Accounting Method)

- 领域 Domain: Phase 21 提交信息的固定句式：'纯增量并入主库 (1112->1122 modes), 10+10 双语场景 (1183->1193), scenario_tags +40 (1690->1730), code_maps figure entry (figures 126->127)'——四个总量、前值后值、增量数一次写清；验收脚本以基线计数为断言（'主库当前 %d modes'）；归档复检进一步在指定 git 对象上验证基线（'基线计数 (1102/1173/1650/125) 在 9c512e6 git 对象上验证以隔离并行未提交增量'）——账不仅在提交里，还能在历史任意时点重放

- Domain: The fixed formula of Phase 21 commit messages: 'pure increment into the main library (1112->1122 modes), 10+10 bilingual scenarios (1183->1193), scenario_tags +40 (1690->1730), code_maps figure entry (figures 126->127)'—four totals, before and after, increments written in one breath; acceptance scripts assert on the baseline ('main library now %d modes'); archive rechecks go further, verifying baselines on specified git objects ('baselines 1102/1173/1650/125 verified on git object 9c512e6 to isolate parallel uncommitted increments')—the books live not only in commits but replayable at any point in history


### 定义 / Definition

基线记账法的核心命题是：一个不断扩张的集合若没有'总数'这个最低限度的账，任何异常（丢失、重复、越界）都只能靠逐条清点才能发现——而逐条清点在千级规模上不可执行。无账的失败机制在于：并行作业下的每一次小合并都'看起来没事'，但四个家族并行后总数对不上，无人能说出是哪一手丢的——异常的归因成本随时间指数上升。操作程序有三步。第一步，选定账目：确定哪些总量是关键账目（本库：modes、scenarios_zh、scenarios_en、scenario_tags、figures）——账目要少而硬，每项都可程序化清点。第二步，双值入账：每次合并前后各记一次值，增量数=差值——'1112→1122'的句式使任何读者一眼核出这次合并的规模与方向。第三步，历史重放：账目不仅写在提交里，还要能在任意历史提交对象上重算验证——复检者可以验证'当时在 9c512e6 上数出来就是 1102'，从而把并行未提交的增量隔离在审计之外。深意有三重。其一，这是竺可桢'账本自治'与茅以升'工程档案'在规模维度的合流：账本记状态、档案记事件、基线记账把两者缝在提交链上。其二，记账使'并行'变得可审计：多任务同时推进时，每个任务只对自己区段的增量负责，总数账充当并行一致性的事后裁判。其三，'账不平即出事'的翻转价值在于它把异常从'将来某天会发现'提前到'合并当场就会暴露'——丢失 10 条模式这种事故在无账库里可能存活数月，在记账库里活不过一次提交。适用边界：适合一切有总量语义的集合（数据表、资产库、库存、预算）；对无自然总量的自由文档，记账对象可换成目录清单或索引文件。现代对应物：财务的复式记账与试算平衡、分布式系统的向量时钟与一致性检查、数据仓库的行数对账、以及库存管理的永续盘存。

The core proposition: for a constantly expanding collection without even a 'total' as its minimal ledger, any anomaly (loss, duplication, out-of-range) is discoverable only by item-by-item counting—and at thousand-item scale that is unexecutable. The failure mechanism of ledger-less operation: under parallel work every small merge 'looks fine,' yet after four families run in parallel the totals disagree and no one can say which hand dropped what—the cost of attributing anomalies rises exponentially with time. The procedure has three steps. First, choose the accounts: fix which totals are the critical ones (here: modes, scenarios_zh, scenarios_en, scenario_tags, figures)—accounts few and hard, each programmatically countable. Second, book both values: record the total before and after every merge, increment as the difference—the '1112→1122' formula lets any reader verify a merge's scale and direction at a glance. Third, replay history: the books live not only in commits but recomputable on any historical object—the rechecker can verify 'on 9c512e6 the count really was 1102,' isolating parallel uncommitted increments outside the audit. Three layers of depth. First, the confluence of Zhu Kezhen's ledger self-governance and Mao Yisheng's engineering archive at the scale dimension: the ledger records states, the archive records events, baseline accounting sews both onto the commit chain. Second, bookkeeping makes parallelism auditable: with many tasks in flight, each owns only its range's increment, and the total ledger serves as the after-the-fact judge of parallel consistency. Third, the inverted value of 'books out of balance means something happened' is that anomalies surface at the merge itself, not 'someday'—losing ten modes could survive months in a ledger-less library; in a bookkept one it cannot survive a single commit. Boundaries: it suits any collection with total semantics (tables, asset libraries, inventory, budgets); for free documents without natural totals, account over directory listings or index files. Modern counterparts: double-entry bookkeeping and trial balance, vector clocks and consistency checks in distributed systems, row-count reconciliation in warehouses, perpetual inventory.

- Domain: The Phase 21 closing triptych: first, the FINAL sync (commits 7b42239/e35bf6a)—boards and workspace mirrors pulled level ('byte-level identical with the boards repo'), the cross-repo catch-up of 230→442→792 modes declared on baseline accounts; second, the final checklist—four assertions ('792 mode IDs all unique, related_modes zero dangling, dual-mirror sha256 identical, QA 15/15 PASS') as the sealing condition; third, the retrospective on paper—every incident along the way (the Phase 22 adjudicated restore, the H-WZ quarantine, the ZKZ repair) left in commits and reports—the closing ceremony promoting a patch history into an institutional history


### 定义 / Definition

收官复盘法的核心命题是：阶段边界是知识的断层线——若不显式封版，上一阶段的松动会伪装成下一阶段的'起点状态'被继承。无收官仪式的失败机制在于：'差不多做完了'的阶段永远差最后 5%，遗留缺陷以'已知问题'名义无限期存续，镜像/基线/引用的松动在无人观看的窗口累积。操作程序有三步。第一步，FINAL 同步：把所有平行演化的副本（多仓、多镜像、多工作区）拉回字节一致——封版的前提是'只有一个当前态'。第二步，终检清单：以最严的断言组合（唯一性、完整性、一致性、验收全 PASS）逐项检查——封版检查的强度必须高于日常检查，因为封版态将成为下阶段的基线。第三步，复盘成文：把本阶段的缺陷、修复、争议与裁定写成报告并随库封存——复盘不是会议纪要而是可检索的制度文献。深意有三重。其一，这是茅以升'复盘归档'工序与竺可桢'日记'传统的阶段化合流：事件史（提交）与状态史（基线）在封版点交汇成可考的'断层线'。其二，复盘成文改变了组织记忆的形态：'上次为什么改这个'不再依赖当事人的记忆，而是依赖随库检索的裁定记录——多智能体协作因此可以跨会话继承教训而非重犯错误。其三，封版使'重启'变得便宜：下阶段从字节一致的基线出发，不需要先考古再开工——收官的成本换来的是下一程的零启动成本。适用边界：适合一切有阶段性的工程（版本发布、学期、战役、迁移）；对永续流式工作，封版可退化为'周期性快照'。现代对应物：版本的 release 流程与 release notes、敏捷的 retrospective、战役的战后总结、以及财务的年结与审计。

The core proposition: phase boundaries are a knowledge system's fault lines—without an explicit seal, the previous phase's looseness is inherited disguised as the next phase's 'starting state.' The failure mechanism of no closing ceremony: the 'nearly done' phase forever lacks its last five percent; leftover defects persist indefinitely as 'known issues'; slack in mirrors, baselines, and references accumulates in unwatched windows. The procedure has three steps. First, the FINAL sync: pull all parallel-evolving copies (repos, mirrors, workspaces) back to byte equality—the premise of sealing is 'exactly one current state.' Second, the final checklist: run the strictest assertion set (uniqueness, completeness, consistency, all-PASS verification)—the sealing check must exceed daily checks in strength, because the sealed state becomes the next phase's baseline. Third, the retrospective on paper: write the phase's defects, fixes, disputes, and adjudications into a report sealed with the library—the retrospective is not meeting minutes but searchable institutional literature. Three layers of depth. First, the phase-level confluence of Mao's 'archive the lessons' step and Zhu Kezhen's diary tradition: event history (commits) and state history (baselines) meet at the seal into a datable fault line. Second, written retrospectives change the form of organizational memory: 'why was this changed last time' no longer depends on a person's memory but on searchable adjudication records sealed with the library—multi-agent collaboration can inherit lessons across sessions instead of repeating errors. Third, sealing makes restarting cheap: the next phase sets out from a byte-identical baseline without archaeology first—the closing's cost buys the next leg a zero startup cost. Boundaries: it suits all phased work (releases, semesters, campaigns, migrations); for perpetual streaming work, sealing degrades to periodic snapshots. Modern counterparts: release processes and release notes, agile retrospectives, post-campaign after-action reviews, fiscal year-ends and audits.

### 流程 / Process

1. 拉平副本：FINAL 同步把多仓/多镜像/多工作区拉回字节一致——唯一当前态 / Level the copies: the FINAL sync pulls repos, mirrors, and workspaces to byte equality—exactly one current state

2. 终检封版：以最严断言组合（唯一/完整/一致/全 PASS）逐项检查——封版态即下阶段基线 / Seal by final check: run the strictest assertions (uniqueness/completeness/consistency/all-PASS)—the sealed state is the next baseline

3. 清零门禁：封版前所有已知缺陷必须清零或显式豁免登记——'已知问题'不得带入封版态 / Zero as a gate: all known defects zeroed or explicitly waived before sealing—'known issues' may not enter the sealed state

4. 复盘成文：缺陷、修复、争议、裁定写成随库报告——制度文献可检索 / Write the retrospective: defects, fixes, disputes, adjudications as reports sealed with the library—institutional literature, searchable

5. 基线入账：封版时点记录全部关键总量与哈希——下阶段的双值入账有了前值 / Book the baseline: at sealing record all key totals and hashes—the next phase's double-value entries gain their 'before' values

6. 豁免清单：确实修不完的项显式列为豁免并写明风险与期限——遗留必须可见且有主 / List the waivers: items truly unfixable explicitly waived with risk and deadline—leftovers visible and owned

### 现代应用 / Modern Applications

- 版本发布：release 前跑全量回归、写 release notes、登记 known issues——封版三件套的标准软件形态 / Version releases: full regression before release, release notes written, known issues registered—the sealing triptych in its standard software form

- 项目收尾：结项时做复盘会并产出可检索的复盘文档——'下次注意'变成'下次查这条' / Project wrap-ups: a retrospective meeting producing searchable documents—'be careful next time' becomes 'look up this entry next time'

- 学业/战役总结：阶段结束写'错题本+裁定记录'——本库的错题本体系正是收官复盘法的教育形态 / Academic or campaign summaries: at phase end write the mistake-book plus adjudication record—this library's error-book system is the closing retrospective in educational form

- 迁移收官：系统迁移完成后双跑对账一周再切流——'封版前的清零'在数据领域是双跑验证 / Migration finales: after cutover, dual-run reconciliation for a week before switching traffic—'zeroing before the seal' becomes dual-run validation in data terms
