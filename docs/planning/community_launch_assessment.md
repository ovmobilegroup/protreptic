# 社区运营启动评估（Community Launch Assessment）

> 评估对象：`docs/10-community/thinking_community_ops_plan.md`（v1.0 · 2026-07-12 · 789 行）
> 评估时间：2026-09-21 · 评估人：Magallanes（基于仓库与线上的**实测**，非推测）

---

## 0. 一句话结论

> **现在还不该启动社区。** 方案本身写得完整，但它假定了一个**并不存在的前提**——
> 一个"已经在被人使用、且有人愿意审核"的项目。
> 实测：项目对外**采用度为 0**（stars 0 / forks 0 / watchers 0 / issues 0），
> 连 README 都还是"Phase 20 变更日志"而非项目介绍。
> **第一步不是搭社区，是先让第一批人用起来。**

## 2. 方案的三个前提，与现实不符

| # | 方案假定 | 现实 | 后果 |
|---|---|---|---|
| **P1** | 「值班审核者」每日 9:00 审 PR、24h 内响应 | **审核者只有创始人 1 人**（无外部贡献者） | §4.1 的日常节奏**无法执行** |
| **P2** | 内容模型「41 种模式」（第 489 行认证考试） | 实际 **2868 条模式 / 278 人物** | 认证/学习月等内容**全部对不上号** |
| **P3** | 先搭仓库/频道/规则，再邀请种子用户 | **仓库/规则早已就绪**，但**采用度 0** | 方案在"已完成的步骤"上又规划了一遍 |

> 方案自己的风险矩阵也承认：**「运营者精力不足」概率 = 高**（第 710 行）。
> 这不是意外，是结构性的 —— **社区运营是持续人力投入，不是一次性交付**。

## 3. 成本诚实估算（按"单人、兼职"口径）

| 阶段 | 方案原估 | 现实修正 |
|---|---|---|
| 建仓库/规则/模板 | W1-W4 | **已完成**（仅差 PR 模板 + README 重写） |
| 邀请 10-20 种子用户 | W5-W6 | **取决于渠道**，非工程问题 |
| 首个"思维挑战" | W7-W8 | 单人可做，但**没人参与就是自嗨** |
| 日常审核 30min/天 + 每周活动 | 隐含 | **≈3-5 小时/周**，且**无人可分担** |
| 12 周种子期总投入 | — | **≈40-60 小时**（且多数是运营而非工程） |

**结论**：Phase 1 的 12 周计划，本质是**为团队写的**。单人执行的代价是 **持续每周数小时**，且**在 0 用户时几乎全是空转**。

## 4. 建议的路径：先补前提 → 探针 → 再决定

### 第 0 步：补三个前提（工程活，可派船员，约 1 天）

1. **重写 README**：从"Phase20 日志"改成真正的项目介绍
   —— 是什么 / 有什么（278 人物 · 2858 模式 · 可点击出处 · 可信度四态）/ 站点链接 / 怎么用 / 怎么贡献
2. **站点加"贡献"入口**：导航 + 页脚指向 `CONTRIBUTING.md` 与 issue 模板
3. **口径对齐**：LICENSE（MIT）与运营方案（CC BY-SA）**二选一**，全库统一
   （注意：改为 CC BY-SA 会影响已有内容的再分发条款，需你定）

### 第 1 步：分发探针（2-4 周，真正的"启动"）

- **接入访问统计**（无它则无法判断任何结果）
- 在**一个**你熟悉的渠道发一次（知乎 / 微信 / V2EX / 小红书 —— **由你选**）
- **只看两个数字**：来了多少人、有没有人提 issue 或 PR

### 第 2 步：按信号决定

| 探针结果 | 行动 |
|---|---|
| 有真实互动（issue/PR） | 启动一个**缩小版** Phase 1：先建 1 个频道 + 1 个审核者（你）+ 只做"案例征集"一个活动 |
| 只有流量、无互动 | 说明**内容/入口**有问题，回头改产品，不是改社区 |
| 基本没人来 | 问题在**分发渠道**，不在社区机制 —— 别搭社区 |

### 第 3 步：如果真启动，先重写方案

现有 789 行方案要按**现实**改写：规模（2868 而非 41）、单人运营、只保留能自动化的部分
（排行榜/周报可脚本化，**"值班审核"没有值班的人**）。
