## 一、为什么需要定期更新

知识体系不是静态文档，而是一个**活的工具库**。随着使用深入，你会不断发现：

- **高频模式**：哪些思维模式你用得最多，应该放在更前面
- **实战案例**：你在什么场景验证了某个模式的有效性
- **空白领域**：某些场景还没有对应的思维模式
- **过时内容**：某些模式的描述不够准确或完整
- **新发现**：从新书、新文章中提炼的新思维模式

定期更新确保这个体系始终与你当前的需求同步。

## 三、贡献流程

贡献流程的设计原则：**越低摩擦越好**。每次贡献不超过 5 分钟。

### 3.1 新思维模式采集

当你从一本书、一篇文章或一次讨论中发现新的思维模式时：

#### 步骤 1：随手记录（2分钟）

创建一个临时文件，填入以下格式：

```markdown
---
name: {模式名称}
category: {领域}
date: YYYY-MM-DD
source: {来源：书名/文章名/对话}
---

# {模式名称}

## 一句话定义
{用一句话概括这个思维模式的核心}

## 思维公式
{如果有的话，写出可复用的公式或框架}

## 操作步骤
1. {第一步}
2. {第二步}
3. {第三步}

## 适用场景
{在什么情况下使用}

## 与其他模式的关系
{与现有模式的关联或区别}

## 实战示例
{一个简单的例子}
```

#### 步骤 2：放入待审核区

将文件保存到 `本体系/extras/pending/` 目录。

#### 步骤 3：季度审核时整合

在下一次季度回顾时，审查 `pending/` 目录中的所有文件，决定：
- **采纳**：合并到对应的 source 文件或创建新源文件
- **修改**：调整后纳入
- **暂存**：暂时保留在 pending/，继续观察

### 3.2 实战案例提交

当你觉得某个思维模式在某次实战中效果特别好：

#### 一键提交格式

直接在任意 Hermes 会话中发送：

```
/contribute case
场景：{什么问题}
模式：{#编号 + 名称}
结果：{达成了什么}
教训：{学到了什么}
```

这会自动生成一条结构化记录，存入 `本体系/extras/cases/` 目录。

#### 案例归档格式

```markdown
## {YYYY-MM-DD} {简短标题}

- **场景**：{描述}
- **使用的模式**：{编号 + 名称}
- **结果**：{效果}
- **效果评分**：⭐⭐⭐⭐⭐（1-5星）
- **来源会话**：{会话链接或ID}
```

### 3.3 版本管理

知识体系采用 **语义化版本号** 管理：

```
主版本.次版本.修订号
  │      │      │
  │      │      └─ 小修：错别字、格式调整
  │      └──────── 新功能：新增模式、技法、案例
  └─────────────── 重大重构：体系结构调整、大规模重写
```

#### 版本规则

| 变更类型 | 版本号变化 | 示例 |
|---------|-----------|------|
| 修正错别字、格式调整 | 1.0.**0** → 1.0.**1** | patch |
| 新增思维模式、写作技法 | 1.**0**.1 → 1.**1**.0 | minor |
| 大规模重构、体系升级 | **1**.0.1 → **2**.0.0 | major |

#### 版本发布流程

```
1. 收集本季度所有变更（来自 pending/、cases/、review notes）
2. 确定版本号升级类型
3. 更新 本体系/README.md 中的版本号
4. 更新 quick_reference.md 的"最后更新"日期
5. 在 extras/releases/ 创建版本摘要
6. （可选）推送技能包更新
```

#### 版本摘要模板

```markdown
# 版本 {VERSION} 发布说明

发布日期：YYYY-MM-DD
版本类型：major / minor / patch

## 新增
- {变更1}
- {变更2}

## 修改
- {变更1}
- {变更2}

## 废弃
- {被移除或合并的内容}

## 已知问题
- {当前未解决的问题}
```

## 四、激励机制

让贡献变得有成就感，而不是负担。

### 4.1 即时反馈

| 行为 | 反馈 |
|------|------|
| 提交一个新思维模式 | 获得 `🧠 架构师` 徽章 |
| 提交 5 个实战案例 | 获得 `📝 记录官` 徽章 |
| 完成一次季度回顾 | 获得 `🔄 守护者` 徽章 |
| 发现并修复一个错误 | 获得 `🔍 纠错者` 徽章 |
| 贡献的模式被正式采纳 | 获得 `⭐ 贡献之星` 徽章 |

### 4.2 季度排行榜

每季度末在 `extras/reviews/` 中记录：

```markdown
# Q{N} {YEAR} 贡献榜

| 排名 | 贡献者 | 新模式数 | 案例数 | 总积分 |
|------|--------|---------|--------|--------|
| 1    | Protreptic   | 2       | 5      | 120    |
| 2    |        |         |        |        |
```

**计分规则**：
- 每个新模式：50 分
- 每个实战案例：10 分
- 完成季度回顾：20 分
- 发现并修复错误：5 分

### 4.3 里程碑奖励

| 里程碑 | 奖励 |
|--------|------|
| 累计 10 个新模式 | 在 README 中添加专属致谢章节 |
| 累计 50 个实战案例 | 创建独立的案例库文件 |
| 累计 100 个思维模式 | 体系升级到 2.0 |
| 连续 4 个季度完成回顾 | 获得"终身守护者"称号 |

### 4.4 心理激励

- **可见性**：每个采纳的模式在文档中标注 `— 由 {姓名} 于 {日期} 贡献`
- **影响力**：季度回顾中展示"本月最常用模式"，让贡献者看到自己的成果被广泛使用
- **成长性**：每次回顾都是一次自我审视的机会，帮助你更了解自己的思维习惯

## 五、操作流程一览

### 日常贡献（≤ 5 分钟）

```
发现新模式/案例 → 随手记录 → 存入 pending/ 或 cases/
```

### 季度回顾（30-45 分钟）

```
1. 检查 pending/ 目录 → 审核并整合
2. 检查 cases/ 目录 → 选取最佳案例
3. 运行使用统计 → 填写模板 A 部分
4. 识别空白领域 → 填写模板 C 部分
5. 提出更新建议 → 填写模板 D 部分
6. 更新版本号 → 发布版本摘要
```

### 年度大修（2-3 小时）

```
1. 汇总 4 个季度的回顾
2. 重新审视知识体系整体结构
3. 决定是否需要体系级升级（major version bump）
4. 清理过时内容
5. 更新 README 和快速检索表
```
